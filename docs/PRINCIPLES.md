# 취업준비 기본 원칙

이 원칙은 [최종 목표와 운영팀](./GOAL_AND_TEAM.md)의 채용 성과 목표 아래에서 적용한다. 문서 완성도 자체보다 서류 통과, 면접 통과, 최종 입사 가능성을 높이는 판단을 우선한다.

## 포지셔닝

- 개발 기술을 깊이 이해하는 시니어 AI PM 수준의 판단과 언어를 기준으로 작성한다.
- 이 기준은 서술의 깊이에 관한 것이며 실제 연차, 직책, 구현 경험, 의사결정 권한 또는 성과를 창작하는 허가가 아니다.
- 업무 나열보다 `문제 → 제품·기술 제약 → 대안과 트레이드오프 → 의사결정과 기여 → 검증된 결과`를 우선한다.
- 경험이 뒷받침할 때 제품 전략, 시스템 동작, 데이터 흐름, 모델·에이전트 동작, 연동, 출시와 운영을 연결한다.

## 근거

- 사실관계는 `사용자의 현재 설명 → 원본 자료 → 현재 작업본 → 명시된 추론` 순으로 판단한다.
- 채용사가 요구하는 역량, 사용자가 증명할 수 있는 역량, 현재 근거가 부족한 역량을 구분한다.
- PM이 정의한 요구사항·판단 기준과 엔지니어가 구현한 내용을 구분한다.
- 성과 수치는 측정 범위와 함께 쓰고 추정과 충돌은 표시한다.
- 팀의 결과를 개인의 오너십으로, 제안을 출시 결과로 승격하지 않는다.

## 소스 사용

- 실제 경험·역할·판단·성과가 답변 근거라면 관련 원본을 읽는다.
- 동일 주제의 연속 수정에서는 이미 읽은 원문을 재사용하고, 주제·수치·책임 범위가 달라질 때 다시 확인한다.
- 사실 의미가 바뀌지 않는 문구·화면 위계 수정은 현재 입력을 우선한다.
- 외부 기술 사실은 공식 1차 문서로 검증한다.
- 비공개 공고, 경력 자료, 멘토링 원문과 개인정보는 읽기 전용으로 사용하며 저장소에 커밋하지 않는다.

## 작성

- 실제 메커니즘이나 판단을 지칭할 때만 기술 용어를 쓴다.
- 약어·유행어 나열과 근거 없는 LLM·RAG·Agent 포장을 피한다.
- `기획했다`, `개선했다`, `협업했다`를 구체적인 기준·결정·조율·변화로 바꾼다.
- 채용 담당자에게는 제품·사업 임팩트를 먼저, 기술 면접에서는 시스템 제약과 판단 근거를 더 깊게 설명한다.

## 저장소 경계

- 이 저장소에는 일반화된 원칙, 라우팅, 비민감 템플릿과 반복 작업 정의만 둔다.
- 개인별 상태, 비공개 소스 URL, 지원서 원문, 회사 내부 문서는 두지 않는다.
